[ DAY 02: ARP OBSERVATION, PING & CACHE EXPERIMENT ]
Date: November 15, 2026
Commands Used: ping 192.168.0.1, arp -a, arp -d

--------------------------------------------------------------------------------
1. CORE DAY 2 TARGETS (DEFINITIONS & MY VALUES)
--------------------------------------------------------------------------------

1. Ping (ICMP Echo Request/Reply)
   - My Result  : 4 Sent, 4 Received, 0% Loss (Avg: 0ms, TTL: 64)
   - Definition : A network diagnostic tool that sends tiny test packets (ICMP)
                  to another device to check if it is reachable and measure speed.

2. ARP (Address Resolution Protocol)
   - My Result  : Mapped 192.168.0.1 -> e8-65-d4-9a-74-b0
   - Definition : The translator between Layer 3 (IP) and Layer 2 (MAC). It asks
                  "Who has this IP?" on the local network to get its MAC address.

3. ARP Cache (ARP Table)
   - My Result  : Interface 192.168.0.107 --- 0x3
   - Definition : A temporary memory list on my PC storing recently discovered
                  IP-to-MAC address pairs so it doesn't have to ask every time.

4. Dynamic vs. Static ARP Entries
   - My Result  : 192.168.0.1 (dynamic) | 192.168.0.255 (static)
   - Definition : Dynamic entries are learned automatically and expire over time;
                  static entries are permanent rules (like broadcast/multicast).

--------------------------------------------------------------------------------
2. COMPLETE EXPERIMENT & COMMAND BREAKDOWN (MULTILEVEL NOTES)
--------------------------------------------------------------------------------

A. Ping Connectivity Test (ping 192.168.0.1)
   1. Payload Size : 32 bytes
      - Note: Standard Windows ICMP test packet size sent to the router.
   2. Round Trip Time (RTT) : <1ms to 2ms
      - Note: Extremely fast response proving a direct, healthy local wired link.
   3. TTL (Time To Live) : 64
      - Note: Packet hop counter; 64 is the standard starting value for Linux/
              embedded router operating systems (like my MT-Link router).
   4. Packet Loss : 0% (4/4 packets returned)
      - Note: Confirms stable Layer 3 communication with the default gateway.

B. ARP Table Inspection & Cache Flush Experiment (arp -a & arp -d)
   1. Initial Cache State (arp -a) :
      - Note: Showed 192.168.0.1 mapped to e8-65-d4-9a-74-b0 (dynamic), along
              with broadcast (ff-ff-ff-ff-ff-ff) and multicast (01-00-5e-...) MACs.
   2. Flushing the Cache (arp -d) :
      - Note: Executed in Administrator PowerShell to wipe all dynamic IP-to-MAC
              mappings from my PC's memory.
   3. Triggering Rediscovery (ping 192.168.0.1) :
      - Note: Because the MAC address was wiped, my PC had to broadcast an ARP
              request ("Who has 192.168.0.1?") before sending the ping packets.
   4. Post-Ping Verification (arp -a) :
      - Note: 192.168.0.1 -> e8-65-d4-9a-74-b0 immediately reappeared as a
              dynamic entry, proving automatic Layer 2 address resolution works.

C. Key Takeaways & Security Relevance
   1. Layer 2 & Layer 3 Teamwork :
      - Note: Software uses IP addresses (Layer 3), but network cards need MAC
              addresses (Layer 2) to actually deliver frames across the wire.
   2. Security Implication (ARP Spoofing) :
      - Note: Because ARP trusts any reply on the local network without checking
              identity, attackers can send fake ARP replies (MITM attacks).

    11    18 ms    18 ms    18 ms  dns.google [8.8.8.8]
   Trace complete.

2. HOP-BY-HOP EXPLANATION & MECHANICS:
   - How Traceroute Works:
     * Sends packets with incrementally increasing Time-To-Live (TTL) starting at 1.
     * Each router along the path decrements TTL by 1. When TTL hits 0, the router discards the packet and returns an `ICMP Time Exceeded` message, revealing its IP address and round-trip time (RTT).
   - Breakdown of My Trace:
     * Hop 1 (`192.168.0.1`): Local home router / Default Gateway (exiting my private LAN).
     * Hop 2 (`192.168.100.1`): ISP local modem gateway / bridge interface.
     * Hop 3 (`205.164.139.1`): ISP local aggregation router.
     * Hops 4–7 (`125.209.115.121`, `149.40.227.188`, etc.): MultiNet ISP core carrier routing infrastructure and regional gateways in Pakistan.
     * Hops 8–10 (`142.250.x.x`, `74.125.x.x`): Google edge network and global transit backbone routers.
     * Hop 11 (`8.8.8.8`): Google Public DNS destination server replying with an ICMP Echo Reply.

3. WPA2 4-WAY HANDSHAKE CAPTURE & OFFLINE AUDIT CONCEPTS:
   - EAPOL Handshake Structure:
     * Consists of 4 cryptographic frames exchanged between an Access Point (AP) and a client when joining a WPA2-PSK network.
     * Message 1 & 2: AP sends ANonce; client replies with SNonce and a Message Integrity Code (MIC).
     * Message 3 & 4: AP confirms group keys and finalizes the secure session.
   - Offline Dictionary Auditing (Aircrack-ng):
     * Because the 4-way handshake contains the PMK (Pairwise Master Key) derivation inputs, an attacker can capture the handshake over the air once and test candidate passwords offline against the handshake hash without generating further wireless traffic or locking out legitimate users.

[ DAY 09: DELIBERATELY VULNERABLE TRAINING LAB - REFLECTION & HEADERS AUDIT ]
================================================================================
Date: November 23, 2026
Host: DESKTOP-S4UPLER
Working Directory: day9-vuln-lab/
Server Command: python .\day9-vuln-lab\vuln_demo.py (127.0.0.1:8090)

1. ENDPOINT TESTING & OBSERVATIONS:
   - `/reflect-unsafe?name=<b>test</b>` returned
     `<p>Welcome, <b>test</b></p>` and exposed
     `X-Powered-By: Day9-Insecure-Demo/0.1`. The parameter was reflected into
     HTML without encoding, and the response disclosed an implementation
     identifier.
   - `/reflect-safe?name=<b>test</b>` returned
     `<p>Welcome, &lt;b&gt;test&lt;/b&gt;</p>`. The characters were HTML-encoded,
     so the supplied markup was treated as text. The response also included
     `Content-Security-Policy: default-src 'self'`.
   - `/debug-info` returned JSON exposing `bound_interface` (`127.0.0.1`),
     `port` (`8090`), and the lab note (`HTTP 200`).

2. SECURITY CONCEPTS & TAKEAWAYS:
   - **Reflected input:** Data from a request parameter that is included in the
     response. Rendering it as raw HTML can create cross-site scripting (XSS)
     risk when an attacker-controlled value is interpreted by a browser.
   - **Context-aware output encoding:** Escaping HTML characters with
     `html.escape` converts markup delimiters to text entities and prevents
     this reflected value from being interpreted as HTML in the tested
     context.
   - **Security headers:** A Content Security Policy (CSP) can restrict which
     resources a page may load. `X-Content-Type-Options: nosniff` and
     `X-Frame-Options: DENY` are additional examples that help reduce browser
     content-sniffing and framing risks.
   - **Information disclosure:** Removing or limiting `X-Powered-By` and
     restricting debug endpoints reduces implementation details exposed to
     clients.
   - **Safe lab boundary:** Binding the demonstration server to `127.0.0.1`
     keeps this exercise local to the host; it should remain a deliberately
     vulnerable training demo and not be exposed as a production service.

     process-to-port auditing, context-aware output encoding, restricted debug
     information, and security headers contribute to layered defenses.
